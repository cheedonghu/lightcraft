# AI companion history storage

The companion owns `companion/`; it does not change the core Catalog format or add catalog operations. Fresh conversations use `companion/state.json` version 2 (`photo-head-v2`). The root contains no photo array. A photo's `HEAD.json` points to one immutable manifest. Existing version 1 remains on its compatibility path until the migration implementation.

## Pages and records

The manifest contains counts and roots for messages, round summaries and round records. Index files are at most 32 KiB and 128 entries; current writers pack at most 32 entries to leave room for the bounded jump table. Each index links its predecessor and up to 64 verified binary ancestor references. A page seek has at most 128 index visits and stops with an actionable error if a damaged/unsupported chain cannot satisfy this bound. No history is removed by that error.

Packed data files are at most 4 MiB. Large logical records stream over consecutive files; those files use a payload of `4 MiB - 32` bytes plus a 32-byte hexadecimal digest trailer. `Entry.chunk_payload` selects this layout; absent means the original packed layout. `PhotoHeader.metadata_chunk_payload` uses the same convention for large metadata. Readers validate chunk digests before displaying fragments and validate the complete record digest and JSON when committing. File reservations still name the contiguous transaction sequence; no additional hash files are created.

These are I/O engineering bounds, not a local history quota. A logical record may be larger than a block. A UI page scans at most 32 records and retains at most 256 KiB plus a bounded ordered item list; oversized message text remains readable in consecutive decoded UTF-8 fragments. New entries include an optional `text_range` byte span in their serialized record; this avoids exposing record metadata in the text view, preserves escaped Unicode/newlines and excludes the same local execution-detail suffix as ordinary messages. The ordered `HistorySlice.items` interface references the owned record/fragment buffers with logical record identity and continuation offset; callers render those items in sequence before the current mutable tail. Forward continuation retains every visible character; the older control returns to that message’s beginning. The full-value compatibility reader and materialized pages have a 32 MiB allocation budget and direct callers to fragments/streaming when it is exceeded. That refusal does not prevent storage or delete records. Large metadata is retained on disk and deferred by the small header reader, without fabricating a checkpoint.

## Actual client path

`companion_photo_header`, `companion_metadata` and `companion_history_slice_at` replace eager whole-conversation loading. `Conversation.view` owns a single bounded history page, while its mutable tail contains only the new round's generated records. Saved inactive read caches are limited to 16 photo entries and a 2 MiB target; the selected current round and dirty unsaved results are runtime data, separate from the read cache. Each subsequent submission seals the completed tail into an immutable prefix before appending its new request. Dirty unsaved results are preserved rather than evicted after a real disk failure.

`save_companion_tail` reuses an immutable verified prefix, writes the changed tail and metadata, verifies the new suffix, then publishes the photo HEAD. It does not reread or rewrite every older record. Late input and execution receipts for a sealed round patch only the bounded recent round-index suffix, preserve the current durable eligibility flag, and survive subsequent tail saves. The immutable manifest marks the patch ordinal so commit verification cannot silently skip the changed record. A failed tail is retained per photo in the archive retry queue; another photo can commit independently. A retry reuses an uncommitted transaction's durable reservation. Ordinary mutation invalidates both the dirty tail's checkpoint and the independent stored revert marker.

Native page reads use one independent Store reader and a bounded result channel. Model-input history uses a separate reader and a captured immutable header. Results carry the exact runtime photo/library and graph/round identity. Switching libraries or stopping a preflight prevents its result from creating a request or publishing a photo. Public poll holds at most eight completed worker results until their exact producer retires, then verifies job identity before publishing parameters or HTTP feedback. This prevents valid next phases from overtaking a still-retiring producer without clearing busy flags early. Local-only preflight stop, enqueue rejection and lost completion after worker retirement release their task lease; the reader remains busy until it retires. The panel does not synchronously scan complete history. Native page navigation keeps one latest desired request while a preceding reader retires, with monotonically increasing request identity in addition to photo/library/header checks. Obsolete completion cannot overwrite the latest cursor, and default initial newest-page loading cannot overwrite an explicit pending request. There is only one page reader and one pending request; its immutable headers remain bounded.

## Model input and follow-on callers

The model service limits remain separate: 1,024 messages, 256 KiB of text/tool arguments, 256 images and a 32 MiB history body. Projection reads one message at a time on the native worker, checks cumulative budgets and predicted Base64 size before hydrating previews, and rejects overflow while keeping every local record. Complete tool-pair legality and exact final request validation belong to the projection implementation.

Round readers should use `companion_rounds_page` or advance `companion_round_search` in bounded steps. `companion_round` is a small recent-record compatibility lookup; an older large-history lookup returns an explicit request to use the paged API. Captured readers must be treated as readers of immutable graph objects until actual worker retirement when adding retirement/GC, including clear/navigation races that release the UI prefix before a cancelled read physically finishes. `pin_companion_prefix` retains at most 32 runtime roots; `companion_retained_headers` also includes a dirty tail’s frozen prefix. Retirement must preserve those manifests and reachable objects until release/close. Recovery and migration must preserve optional jump/chunk/record-patch fields and pending revert overrides, reservation ownership and a photo's single HEAD commit point.

Validation uses procedural photos, native temporary directories and fault stores. See the UX-08 execution report for actual commands, large-history volume, corruption, seek, cancellation and screenshot evidence. No all-platform durability certification is implied by native macOS tests.


## Storage recovery and retirement

`PendingCommit.content_digest` identifies the caller's logical payload without a second serialized allocation. Retrying the same payload reuses its transaction and reserved highwater. Changed payloads can reuse an unactivated range; once HEAD is visible a genuine next generation receives a new transaction. Before commit, the persisted reservation must still match the caller-held pending object. Commit repeats bounded pending/ownership/HEAD writes to confirm durability even if a previous directory-sync error made the same bytes visible. Pending removal waits for successful root activation and durable ownership transfer; its failure is cleanup debt, not a reversal of a saved conversation. Existing same-round invalidation is preserved by confirmation and ordinary guard invalidation retains its association fields.

Execution/input acknowledgments persist a small exact receipt operation in the pending transaction. A failed operation also remains in the photo's storage retry queue. `Session.persist` can finish it without another transport event; reopening can finish a stored incomplete receipt before accepting a new tail. The reused round-index prefix retains the patch. Recovery never changes develop parameters, starts an AI job, sends content or restores invalidated eligibility.

Each photo's `gc/owners.json` points to linked `gc/owners/<transaction>.json` allocation ranges. An owner is durably linked before pending ownership can disappear. `gc/work.json` stores a restartable marking/sweeping cursor; `gc/marks/<key-digest>.json` stores bounded per-object reachability marks. All retirement files use a known versioned/checksummed envelope. Unknown or damaged checkpoints protect data and return an actionable cleanup error. Small ownership audit nodes remain linked after reclamation; they are tracked metadata, not untracked orphan data.

`Session.collect_companion(photo, budget)` accepts 1–32 work units. Each unit reads a bounded manifest/index/ownership/checkpoint, marks one allocation/reference or attempts one idempotent owned deletion, then persists its cursor. It never lists a directory or builds a whole-history live set. Normal persistence advances two units for one photo at a time, rotates photos and requests later frames at 250 ms while maintenance remains. Actual save failures retain their ordinary 2 s retry backoff. Cleanup errors are photo-local and cannot make an already-saved result become unsaved. `ai.status` reports selected-photo `saveState`, `cleanupPending` and `cleanupError`; the existing unsaved indicator and localized notices show actual effects and storage recovery separately.

Marking captures HEAD, both possible pending graphs, reused prefixes, dirty tails, cached prefixes and actual captured reader roots. A changed snapshot restarts marking before any deletion. An incomplete pending graph pauses deletion rather than guessing its external references. Only numbered blocks/pages/previews and the owned immutable manifest are candidates; independent editor state, revert/certificate guards, migration metadata and other files are never classified as orphan data. New entries carry bounded complete `preview_refs`; unknown/oversized inventories conservatively protect previews until their graph is retired. Shared inherited previews survive replacement and are reclaimed after the last known reference disappears.

Captured native readers retain their immutable graph until the actual `HistoryReader` drops, including cancellation and library close/reopen. `Store.retention_namespace` forwards adapter identity: Unix native directories use device/inode so aliases share protection, MemStore uses its shared backing-instance identity. On Windows, safe stable directory identity is unavailable through the configured stable std interface: native readers share a conservative process protection domain, and physical GC waits until all native readers retire. This delays cleanup while preserving normal reading/saving/editing; foreign-library headers are not mixed into a photo graph. Unknown adapters need a reliable namespace for retained native readers; cleanup remains protected rather than guessing. Windows behavior is source-implemented, not runtime-certified on this macOS host.

Main-frame resumable readers use `Session.retain_companion_history(&captured_header)` before their first read. The opaque `HistoryRetention` belongs to the real view/scan lifetime, including inactive-photo pauses and successive record scans; release it when that view is actually retired. Cancelling a worker or clearing a current prefix does not retire a captured reader. The UX-16 caller binding is verified when its separately reviewed implementation is combined.

After HEAD and revert writes return durable success, the sealed owner node records the confirmed manifest digest before pending removal. A failed proof write is cleanup debt; it does not change saved conversation truth. Runtime cleanup retains the exact successfully published transaction and repeats only the small proof write and pending removal, including errors after visible replacement. A reopened pending transaction without a verified proof remains protected rather than re-verifying a full history in the frame loop; a normal storage transaction retry may still perform its required graph verification.

Native `Session.open_library` readers/views also retain the existing OS `LibraryLock` through the guard. Switching to B does not make A available to another process until A's actual readers retire; B stays usable. Reopening the same current library reuses its lock. A later attempt to reopen a library whose old reader is still alive is refused by the existing lock until retirement. `open_library_in` keeps its documented host-guarded/unlocked contract; unsupported-lock network shares retain their existing explicit limitation. Lifecycle cancellation must still retire actual workers/views, rather than interpreting a cancel flag as completed I/O.
