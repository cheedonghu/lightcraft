# Fork 两人协作与分支管理

适用于两人维护的 LightCraft fork。相邻的 photo-companion 后端采用相同的简化规则；本约定不改变 LightCraft 上游的协作策略。

## 日常开发

- 默认直接在 `dev` 开发，不要求为每个任务创建分支或 PR。
- 开始工作前同步一次远端 `dev`，不要求开发过程中按固定频率同步或提交。
- 尽量拆分需求、减少重叠修改；可验证的小改动完成后提交，推送时机由开发者自行判断。
- 不增加任务报备、模块认领、固定审查或发布审批流程。

## Worktree

- 大任务或开发者明确要求时，创建 worktree 隔离工作；其他任务默认在当前 `dev` 工作区完成。
- Worktree 可以使用临时分支，不要求 detached HEAD，不规定分支命名或合并方式。
- 实现后合回 `dev`，对集成结果执行相关检查。

## 提交检查与既有失败

- `dev` 保持可编译、可运行，已有功能保持可用。
- 代码改动提交前至少检查格式、受影响部分的编译和相关测试；按实际影响范围选择检查，不要求每次执行完整 `cargo xtask ci`。纯文档改动检查内容、链接和格式即可。
- 允许豁免既有失败，但需记录改前提交 SHA、检查命令和失败现象，并确认本次修改没有新增失败。记录放在相关任务或变更说明中，无需另设审批流程。
- 豁免限定到已确认的失败，不因某个测试失败跳过整个模块的验证。
- `cargo xtask ci` 首次失败后会停止；被跳过的相关检查需单独执行，未运行不能算通过。
- MCP 测试失败尚未复现确认，不能仅凭印象认定为既有失败。

## 发布与上游同步

- `main` 作为正式发布分支，发布暂由项目负责人手动处理；agent 不自行向 `main` 合并或推送，不改发布触发和环境配置。
- LightCraft 上游更新由项目负责人定时手动引入 `dev`，其他开发者随后同步 fork 的 `dev`。
- 本约定定义协作规则，不代表现有分支、CI 或原 `release` 发布配置已经迁移。
